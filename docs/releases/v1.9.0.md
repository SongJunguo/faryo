# Faryo 1.9.0

Faryo 1.9.0 moves new Web-managed Codex sessions from terminal-text polling to
the official Codex App Server protocol while retaining existing tmux/TUI
sessions as an explicit compatibility mode.

## Changes

- Streams agent-message deltas into one stable keyed response block, then
  converges in place to the official final item and durable Codex rollout.
- Adds a version-tolerant bidirectional Unix WebSocket client with one reader,
  bounded pending RPCs, reconnect/backoff, capability fallback and fail-closed
  unknown server requests.
- Adds one single-writer session actor per loaded Web thread, a count- and
  byte-bounded cursor journal, replay/gap/snapshot recovery and body-free
  transport metrics.
- Keeps App Server in an independent systemd user service. Restarting Owner can
  preserve an active turn; the browser reconnects and recovers its snapshot or
  final history without a hard refresh.
- Migrates Owner's HTTP/SSE shell from `ThreadingHTTPServer` to Starlette and
  Uvicorn. Protocol, actor, journal, registry, history and authorization rules
  remain framework-neutral Python modules.
- Makes Gateway's Start Codex launcher reflect body-free App Server health and
  replaces its server-rendered loading placeholder on both success and failure.
- Makes nested Owner ES modules inherit the active release revision, so an
  ordinary reload or new tab receives a coherent deployment.

## Compatibility and security

- New sessions started from the Web use `web-managed` ownership. Existing
  terminal sessions remain `terminal-managed`; Faryo does not attach two
  writers to one Codex thread or resize tmux.
- Browser traffic still follows Cloudflare or another identity-aware edge,
  Gateway, and Owner authentication. Codex App Server listens only on a private
  mode-`700` Unix-socket directory and is never exposed by Gateway.
- The replay journal and routine logs contain lifecycle metadata and byte/count
  measurements, not prompt, answer, diff, tool-output, token, Cookie, domain or
  private-path content.
- The small synchronous App Server helper is restricted to terminal-managed
  compatibility operations and cannot start a turn for a Web-managed thread.

## Validation

- Canonical source gate: 219 Owner, 118 Gateway and 60 unified-CLI Python tests,
  plus Ruff, ESLint, Prettier, TypeScript and reproducible local browser bundles.
- Isolated real Codex validation covers protocol initialization, delta/final
  convergence, Markdown, KaTeX, code, body-free replay, JSONL recovery,
  idempotent fast send acknowledgement and an Owner restart during an active
  turn.
- Real browser validation covers stable streaming-node identity, ordinary
  reload, long-history bounds, mobile layout, protected resources, send
  isolation and existing terminal-managed behavior.

## References

The architecture was informed by clean-room study of YepAnywhere, HAPI and the
official Codex App Server schema. No AGPL HAPI implementation was copied. Pinned
commits, licences and adopted/non-adopted ideas are recorded in
[the reference audit](../appserver-streaming-reference-audit.md).

## Candidate status

Superseded by the v1.9.1 deployment candidate. The source and isolated runtime
gates pass. The feature branch remains a release
candidate until the installed Gateway/Owner/App Server path, public-auth
boundary, ordinary reload and every pre-existing tmux pane identity and geometry
pass the deployment gate described in
[the implementation plan](../plans/v1.9-appserver-streaming-plan.md).
