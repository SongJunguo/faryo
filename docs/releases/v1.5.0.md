# Faryo 1.5.0

Faryo 1.5.0 replaces the fork's multi-script, Conda-visible deployment with one
versioned `faryo` lifecycle while preserving the existing Codex/tmux execution
model and private data.

## Highlights

- One CLI now owns `install`, `doctor`, `status`, `start`, `stop`, `restart`,
  `open`, bounded `logs`, checksum-verified `update`, health-gated `rollback`,
  and data-preserving `uninstall`.
- Owner and Gateway run directly as two loopback-only systemd user services.
  The Owner Web process no longer consumes a dedicated tmux session or needs a
  keepalive timer; only real Codex TUIs remain in tmux.
- The installer creates one standard private venv per release below
  `~/.local/share/faryo/versions/`. It never modifies Conda base or system
  Python packages.
- Python 3.10 is now the maintained compatibility floor. CI covers Python 3.10
  and 3.13; Python 3.10 receives the exact `tomli` backport.
- Fresh installation creates missing mode-`600` Owner/Gateway configuration,
  a single local `txy` route, Owner Token, and initial Gateway password. Existing
  private configuration is preserved byte-for-byte across failed installation.
- Tagged releases include a Git source archive, exact SHA-256 manifest, reviewed
  bootstrap, and bootstrap checksum. No binary endpoint package is published.

## Atomic lifecycle and recovery

- Python venvs are created directly in their immutable final version directory;
  only the `current` symlink is exposed atomically after the final-path CLI
  check succeeds.
- Update accepts only approved GitHub HTTPS assets, bounds compressed and
  extracted sizes, rejects links/devices/path traversal, verifies the exact
  archive filename and SHA-256, and checks `RELEASE` plus package version.
- Each service unit pins the active version. Installation, update, and rollback
  snapshot units and private environment files before switching and restore the
  prior version when loopback health checks fail.
- `faryo stop` and all service transitions preserve ordinary tmux sessions and
  their geometry. `faryo uninstall` preserves `~/.faryo` by default; private
  data deletion requires the explicit pair `--purge-data --yes`.

## Install

Download `install-faryo.sh` and `install-faryo.sh.sha256` from this Release,
then review and verify the installer:

```bash
sha256sum --check install-faryo.sh.sha256
less install-faryo.sh
bash install-faryo.sh --version v1.5.0 --workspace /path/to/workspace
```

The script requires Ubuntu/Linux, Python 3.10+ with `venv`, tmux, curl, a
systemd user manager, and Codex CLI. It does not execute sudo or create public
Cloudflare/Tunnel configuration.

## Upgrade from v1.4

If the old dedicated `local-tmux-owner`/keepalive supervisor is still active,
approve migration explicitly:

```bash
bash install-faryo.sh --version v1.5.0 \
  --workspace /path/to/workspace \
  --migrate-owner
```

The migration stops only the named Owner service session, verifies all existing
agent tmux dimensions before and after, and restores the v1.4 supervisor on
failure. It does not stop `faryo1`, `faryo2`, or other Codex sessions.

A clean source checkout can enter the same path without downloading assets:

```bash
PYTHONPATH=src /usr/bin/python3 -m faryo_cli install \
  --workspace "$PWD" \
  --migrate-owner
```

## Verification

- Canonical source gate: 130 Owner, 112 Gateway, and 49 CLI Python tests,
  browser modules, Ruff, ESLint, Prettier, reproducible local UI bundles, and
  zero npm audit findings.
- A real clean-HOME install used Ubuntu's Python 3.10.12, generated private
  mode-`600` config, built a final-path venv, installed both units, and left no
  staging shebang.
- Real direct Owner/Gateway cutover, stop/start/restart, structured desktop and
  mobile pages, long history, Goal, Markdown/TeX, and 20-message idempotent send
  checks retained every pre-existing agent tmux dimension.
- The production diagnostic after private-venv migration reports 20 OK, zero
  warnings, and zero failures; legacy Owner supervision is retired.

## Security boundary

Local installation creates no public ingress. Owner and Gateway stay on
`127.0.0.1`; remote access remains a separate explicit tunnel plus
identity-aware access configuration. Tokens, passwords, email addresses,
domains, paths, session identifiers, and conversation text do not enter release
assets, manifests, CLI JSON, or public validation records.

Rollback changes application code and units only. It does not roll back Codex
history, attachments, login state, tokens, or other `~/.faryo` data.
