# Faryo v1.5 Unified CLI and Service Installation Plan

更新时间：2026-08-20
目标版本：v1.5.0
状态：进行中

## 1. 结论

Faryo v1.5.0 不重写 Owner/Gateway，不引入 Go、Node 后端或 uv，也不要求普通用户理解 Conda。
本版本用一个稳定的 `faryo` 命令吞掉当前分散的 Python 环境、初始化脚本、systemd unit、Token、
端口和健康检查，并把后台收敛为：

```text
systemd --user
├── faryo-owner.service
└── faryo-gateway.service

tmux
├── faryo1 / faryo2 / ...
└── 其他用户自己创建的终端会话
```

Owner Python Web 服务不再运行在 `local-tmux-owner` tmux 中，也不再依赖
`faryo-owner-keepalive.timer`。Codex TUI 继续运行在 tmux；Owner 作为同一 Linux 用户的普通
systemd service，通过 tmux socket 控制这些会话。

普通本机用户最终只需要：

```bash
faryo install
faryo doctor
faryo start
faryo open
```

公网 Cloudflare Tunnel/Access 继续是明确的可选第二阶段，安装器默认只建立 loopback 服务，绝不
自动把电脑暴露到公网。

## 2. 当前部署基线与问题

当前真实部署：

```text
faryo-gateway.service
  -> run-gateway.sh
  -> Starlette/Uvicorn Gateway :8780

faryo-owner-keepalive.timer
  -> faryo-owner-keepalive.service
  -> start-web-owner.sh
  -> tmux local-tmux-owner
  -> run-web-owner.sh
  -> Python Owner :8765
```

主要问题：

| 问题 | 当前证据 | v1.5 处理 |
| --- | --- | --- |
| 操作入口分散 | Owner/Gateway init、start、service install、status 分属多个脚本 | 一个 `faryo` CLI |
| Owner 双层托管 | systemd timer 定时维护一个 tmux Web 服务 | 直接 `faryo-owner.service` |
| 普通用户看见 Conda | README 要求创建/激活 Conda 环境 | 安装器创建私有标准 venv |
| systemd 绑定 checkout | unit 写入当前源码绝对路径 | 稳定 `current` symlink + CLI 入口 |
| 更新不可原子回退 | `git pull` 后直接重启 | 版本目录、健康门禁、原子切换与 rollback |
| Python 选择不统一 | 个别诊断路径直接使用 `python3` | CLI 统一解析自己的 private venv |
| Owner service 缺统一安装器 | 只有 keepalive unit 模板 | CLI 生成/安装两个 user units |
| 初始化合同漂移 | Gateway initializer 仍含旧 12h/168h 限制 | 与当前 720h runtime 合同统一并测试 |
| 生产/开发依赖混淆 | Node/Ruff/ESLint 出现在源码开发流程 | 普通安装只装 runtime Python pins |
| 公网步骤混入本机部署 | Tunnel、Access、域名是另一安全层 | `remote` 子命令/文档独立，默认不执行 |

`pyproject.toml` 当前只是 Ruff 配置，不是可安装的 Faryo application package；因此不能假装
`pipx install faryo` 已经可用。v1.5 先建立真实 CLI/package boundary，再决定后续是否发布到
PyPI。`.deb` 也不作为首个交付，因为 root post-install 与用户级 tmux/config/systemd 的所有权
边界更复杂。

## 3. 目标目录布局

普通用户数据与程序严格分离：

```text
~/.local/bin/faryo
~/.local/share/faryo/
├── current -> versions/v1.5.0
├── versions/
│   └── v1.5.0/
│       ├── app/
│       └── .venv/
└── state/
    ├── previous-version
    └── install-manifest.json

~/.config/systemd/user/
├── faryo-owner.service
└── faryo-gateway.service

~/.faryo/
├── owner/config + data
└── gateway/config + state + audit/packages
```

规则：

- `~/.local/share/faryo/versions/*` 是可替换程序；
- `~/.faryo` 是持久私有状态，update/rollback 不迁移、不删除；
- 每个版本保留自己的 venv，避免升级一半污染上一版本；
- `current` 只在新版本依赖、source gate/runtime smoke 和健康检查完成后原子切换；
- 默认至少保留当前与上一版本；清理更旧版本必须显式执行；
- `faryo uninstall` 默认保留 `~/.faryo`，只有 `--purge-data` 才进入破坏性确认。

## 4. CLI 合同

首版使用 Python 标准库 `argparse`，不为少量命令引入 Typer/Click 新依赖。顶层命令：

| 命令 | 行为 | 是否写状态 |
| --- | --- | --- |
| `faryo install` | 检查依赖、创建 private venv/config、安装 units、启动并验收 | 是 |
| `faryo doctor` | 只读检查 Python/tmux/Codex/systemd/端口/权限/健康 | 否 |
| `faryo start` | 启动 Owner + Gateway，等待健康 | 是 |
| `faryo stop` | 停止两个 Web 服务，不停止 Codex/tmux | 是 |
| `faryo restart` | 受控重启并验证 SSE/健康 | 是 |
| `faryo status` | 简洁状态；`--json` 提供无秘密机器可读输出 | 否 |
| `faryo open` | 打开或打印 Gateway URL，不暴露 Owner Token | 否 |
| `faryo logs [owner|gateway]` | 读取 journal，不读取对话正文 | 否 |
| `faryo update [--version]` | 下载/准备版本，验证后原子切换 | 是 |
| `faryo rollback` | 切回 previous version，重启并健康检查 | 是 |
| `faryo uninstall` | 删除 units/程序；默认保留私有数据 | 是 |
| `faryo remote doctor` | 只读检查公网边界；不自动创建 Access/Bypass | 否 |

内部 service 命令不宣传给普通用户：

```text
faryo internal run-owner
faryo internal run-gateway
```

普通用户只调用稳定的 `%h/.local/bin/faryo`。systemd unit 不引用 Git checkout，而是固定到已经完成
安装与验收的确切版本目录和 private venv；update/rollback 原子切换 `current` 后同步重写两个 unit。
这避免某个未完成的链接或包写入在下一次自动重启时改变服务版本。

## 5. 安装边界

### 5.1 运行时前置条件

Ubuntu/Linux maintained path 只要求：

- Python 3.10+；CI 同时验证 Ubuntu 常见的 3.10 与开发主线 3.13；
- `python3-venv`/ensurepip；
- tmux；
- curl；
- Codex CLI；
- systemd user manager；
- 一个当前浏览器。

Git、Node、npm、Ruff、ESLint、Prettier 和 Playwright 是开发/源码验证依赖，不是普通运行依赖。
安装器不自动执行 sudo；缺少系统包时，`doctor` 给出经过检查的 apt 命令，由用户自己确认执行。

### 5.2 Bootstrap

正式文档不能只提供不透明的 `curl | sh`。交付两种入口：

1. 推荐：下载版本化 bootstrap + SHA-256 manifest，先校验再执行；
2. 可选 convenience one-liner：明确说明其网络与 shell 风险，并固定 release tag，不跟随任意 main。

Bootstrap 只负责：

1. 选择确切版本；
2. 下载 source/runtime archive；
3. 校验 manifest/hash；
4. 放入临时 version directory；
5. 创建该版本 private venv 并安装 exact runtime pins；
6. 运行 `faryo install --from-bootstrap`；
7. 成功后原子设置 `current`。

不把 OAuth、Cloudflare API Token、Owner Token、Gateway Cookie secret 或登录密码写入命令行、
日志、GitHub Actions artifact 或公开 manifest。

## 6. Owner 直接 systemd 化

新增 `faryo-owner.service`：

- `Type=simple`；
- `ExecStart=%h/.local/bin/faryo internal run-owner`；
- loopback `127.0.0.1:8765`；
- `Restart=on-failure`，有限退避；
- `UMask=0077`；
- 日志进入 user journal；
- 停止/重启只影响 Owner Web，不执行 `tmux kill-server` 或删除任何 Codex session；
- 通过配置中的 `FARYO_CODEX_BIN`/Agent shell，而不是依赖交互式 NVM PATH；
- service 启动前验证 private env 权限、端口目标和 Python runtime。

迁移完成后退役：

- `local-tmux-owner` service session；
- `faryo-owner-keepalive.timer`；
- `faryo-owner-keepalive.service`；
- 只为维持 Web Owner 而存在的 start/keepalive 链。

Codex 的 `faryoN` tmux sessions、桌面 tmux 和用户的其他 tmux 会话全部保留。

## 7. 当前机器迁移顺序

本机切换必须可回滚：

1. 记录 Owner/Gateway PID、端口、配置权限、健康和所有 tmux geometry；
2. 生成但暂不 enable 新 Owner unit；
3. 在隔离端口运行 direct-systemd-equivalent Owner contract/browser smoke；
4. 停止 keepalive timer，停止且只停止 `local-tmux-owner`；
5. 启动 `faryo-owner.service` 占用 8765；
6. 验证结构化历史、Goal、Markdown/TeX、20-message、附件、Changes、SSE；
7. 验证所有原有 agent panes 尺寸与进程仍在；
8. 切换 Gateway unit 到统一 CLI，复验 public Access boundary；
9. 观察 journal/restart counts；
10. 验收后才删除旧 timer/service 安装文件。

任一步失败：停止新 Owner，重新启动原 `local-tmux-owner`，恢复 timer，不改 `~/.faryo`、Codex
rollout/SQLite、tmux sessions 或 Cloudflare。

## 8. Update 与 rollback

`faryo update` 必须：

1. 下载到受限临时目录，校验 SHA-256、压缩/解压大小、单一根目录、普通文件类型和版本元数据；
2. 校验版本、manifest、runtime requirements；
3. 创建独立 venv；
4. 在隔离端口运行 source/runtime/security smoke；
5. 写入 `previous-version`；
6. 原子替换 `current` symlink；
7. daemon-reload + restart Owner/Gateway；
8. 通过 loopback/browser/public 非破坏性检查；
9. 失败则自动恢复 symlink 和服务。

`rollback` 不回滚用户配置、密码、Token、审计、附件或 Codex 历史；如果新版本引入不可逆配置
schema，必须在相应版本计划中另设迁移门禁，不能隐式跨过。

## 9. 明确非目标

- 不重写为 Go/Rust/Node 后端；
- 不引入 uv；
- 不在 v1.5 首阶段依赖 PyPI/pipx；
- 不先恢复旧 `.deb`/macOS 打包链；
- 不自动执行 sudo/apt；
- 不自动创建 Cloudflare Tunnel、Access application、身份规则或 Bypass；
- 不把 Owner 与 Gateway 合成一个公开进程；
- 不把 Codex 从 tmux 迁出；
- 不修改 Codex 权限模式；
- 不以“安装方便”为由放宽 loopback、CSRF、Cookie、Owner Token 或精确身份边界。

## 10. 实施阶段

### 阶段 A：冻结合同与修复初始化漂移

- 为 CLI 命令、退出码、JSON schema 和不记录秘密建立测试；
- 修正 Gateway initializer 的 720h 合同漂移；
- 所有 runtime/diagnostic 路径统一 Python discovery；
- 建立旧部署状态探测和 migration dry-run；
- source gate 保持现有 Owner/Gateway/browser 矩阵。

### 阶段 B：统一 CLI 骨架

- 建立可安装的 Python application metadata 和 `faryo` console entry；
- 实现 `doctor/status/start/stop/restart/open/logs`；
- 现有脚本变成 CLI service 层的薄兼容入口，随后删除重复实现；
- 提供人类输出与 privacy-safe `--json`。

### 阶段 C：Owner 直接 systemd service

- 新增 direct Owner runner 和 unit；
- 隔离端口 contract；
- 本机 staged cutover + rollback drill；
- 退役 keepalive timer 与 `local-tmux-owner` 生产路径；
- 确认 Codex tmux geometry/process 不变。

### 阶段 D：版本化安装器

- 实现 program/data layout；
- bootstrap、hash manifest、private venv；
- first-run config 合并而非覆盖；
- stable units/current symlink；
- 干净临时 HOME 安装/卸载/保留数据测试。

### 阶段 E：update/rollback

- exact version 下载；
- isolated preflight；
- atomic symlink switch；
- health-gated rollback；
- interrupted install/update recovery；
- 最少 current/previous retention。

### 阶段 F：文档、部署与 v1.5.0 发布

- README 首屏只保留普通用户入口；开发者 source workflow 下沉；
- runbook 分 Local 与 Remote；
- 真实本机从旧架构迁移并验证；
- clean-home installation fixture；
- source-only release 是否继续或增加 checksum/bootstrap assets，在发布前按供应链门禁决定；
- push main、CI、annotated tag、Release。

## 11. 验收矩阵

### CLI

- 所有命令 `--help`、退出码、unknown option；
- `doctor --json` schema 固定且无 path/token/email/password；
- 缺 Python/venv/tmux/Codex/systemd/curl 的精确错误；
- 重复 install/start/stop 幂等；
- 不污染 Conda base 或 system Python；
- shell PATH 缺 NVM 时仍找到已配置 Codex/Node sibling。

### Service

- Owner/Gateway only loopback；
- systemd active、restart count、journal redaction；
- Owner service restart 不停止任何 agent tmux；
- active SSE 下快速停止；
- no keepalive timer/local-tmux-owner after final cutover；
- boot/login lifecycle documented；linger 只在用户明确选择时配置。

### Product regressions

- 130+ Owner、112+ Gateway source tests；
- Markdown/TeX/Shiki、Goal、完整历史、Chat/Raw、Live、Changes、copy；
- 35 attachments + four-way concurrency；
- 20-message/restart/network/504/cross-session idempotency；
- Start/Resume/Rename/Archive/Restore/Close；
- PWA/Fullscreen/mobile document scroll；
- 390x844 与 1440x900 Owner/Gateway；
- 每个矩阵前后 agent tmux geometry 相同。

### 安装/update/rollback

- 空 HOME；
- 已有 `~/.faryo`；
- 当前源码部署迁移；
- 下载/解压/venv/health 中断；
- checksum mismatch；
- current symlink 不完整；
- update 成功与失败自动 rollback；
- uninstall 默认保留数据；
- 配置/Token/password mode 600，目录 mode 700。

### 公网与隐私

- 本机安装绝不产生公网 ingress；
- 现有 Cloudflare 168h、精确邮箱、无 Everyone/Bypass/MFA require 不被 CLI 修改；
- cookie-free public route 仍被 Access 阻断；
- 仓库、安装 manifest、CLI JSON、journal、CI artifact 无真实 domain/email/token/path/正文；
- Owner Token 不进入 URL；Gateway login/CSRF/CSP/HSTS/nosniff 保持。

## 12. 发布条件

只有同时满足以下条件才发布 v1.5.0：

1. 普通用户从空环境可用统一入口完成本机安装；
2. Owner/Gateway 都由直接 systemd user service 管理；
3. `local-tmux-owner` 和 keepalive timer 已退出生产路径；
4. Codex sessions 仍在 tmux 且 geometry/process 不变；
5. install/update/rollback/uninstall 数据边界通过；
6. source/browser/deployed/public/privacy tests 全绿；
7. 当前机器真实迁移与 rollback drill 通过；
8. README、CLI help、runbook、architecture、security、release notes 同步；
9. main 远端 CI 通过；
10. annotated tag 与发布资产/manifest 供应链验证通过。

计划只有在 v1.5.0 Release 和最终 post-release main CI 成功后才改为“完成并部署”。
