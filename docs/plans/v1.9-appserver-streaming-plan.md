# Faryo v1.9 App Server Streaming 实施计划

状态：进行中  
开发分支：`feature/appserver-streaming`  
基线：Faryo `v1.8.6`，`main` 提交 `3243ff01538c570b579c130982b4e5d6d4c1e522`  
开始日期：2026-08-22

## 目标

把 Faryo 从“tmux 文本实时预览 + Codex JSONL 完成后整块刷新”升级为以官方 Codex
App Server 为新 Web 会话运行时的可靠流式架构。用户应在回答产生时持续看到正文，完成时
无跳变地收敛到现有 Markdown/KaTeX/代码高亮结果；短暂网络中断、浏览器休眠或 Owner 重启
不能让正在执行的 Codex turn 消失。

本次是大改动，但采用渐进替换：保留已经稳定的 Preact app shell、移动键盘、历史分页、
富文本渲染、可靠发送和 tmux 兼容路径；新模块达到验收门后才成为新 Web 会话的默认后端。

## 用户可感知结果

- 新 Web 会话直接显示回答正文 delta，不再等 Live from tmux 消失后整块刷出最终回答。
- 网络重连从最后 event cursor 继续；窗口外的断线通过 snapshot 自动恢复，无需强制刷新。
- Owner 更新或重启时，独立 App Server 仍持有活动 turn；页面恢复连接后自动追上最终状态。
- 流式尾部与完成后的 Markdown、TeX、表格、代码和 diff 使用同一个消息位置，不重复、不跳动。
- 审批、请求用户输入、排队消息、Esc 立即发送、Goal、usage 和模型状态通过正式协议进入 UI。
- 既有 tmux/TUI 会话继续可用，Live from tmux 和 raw 模式不回归；页面清楚标识会话由 Web
  还是 Terminal 托管。

## 非目标

- 不让浏览器直连 Codex，也不绕过 Gateway、Cloudflare Access 或 Owner token。
- 不在本阶段让 TUI 和 Web 同时写同一个 thread。
- 不迁移到 React，不复制 YepAnywhere/HAPI 的实现或 UI。
- 不建立 Faryo 消息正文数据库，不改变 Codex JSONL 的权威地位。
- 不自动接管当前正在运行的 tmux/TUI 会话。
- 不修改任何 tmux 窗口尺寸或 TUI 的终端几何。
- 不在活动 turn 中自动重启 App Server 以追随 Codex 更新。

## 不可回归约束

1. **单写者**：一个 Codex thread 同时只有一个运行时 writer。
2. **认证**：外网流量仍为 Browser → Cloudflare/Gateway → Owner；Unix socket 仅本机私有。
3. **持久真相**：Codex rollout/App Server history 是正文最终来源；SSE 环只做短期传输恢复。
4. **发送幂等**：每次用户提交有稳定 client message id / submission id，超时重试不能重复 turn。
5. **终态优先**：final item 必须覆盖同一 streaming item，不能追加第二份回答。
6. **有界资源**：事件环、delta buffer、浏览器 rich DOM 和 pending RPC 都有数量/字节/时间上限。
7. **版本兼容**：未知 notification 可忽略并计数；未知 server request 必须 fail closed。
8. **普通刷新**：所有可变前端资产自动版本化，缺失/拒绝资源 `no-store`，不要求 hard refresh。
9. **隐私**：日志、审计、公开文档和测试 fixture 不含正文、Token、Cookie、真实域名或私有路径。
10. **兼容模式**：terminal-managed 会话继续使用现有 tmux 捕获和可靠 Enter 语义。

## 参考结论

完整审计见 [`../appserver-streaming-reference-audit.md`](../appserver-streaming-reference-audit.md)。

- YepAnywhere：稳定 item identity、实时尾部/持久历史收敛、高频叶节点更新、有界富 DOM。
- HAPI：双向 RPC、单写者切换、SSE epoch/sequence/replay/gap；其 Codex 正文当前不是逐 delta
  提交，因此不照搬 converter。
- OpenAI Codex：Unix socket 多连接、thread/turn/item 生命周期、双向 server request、分页历史、
  断线后 resume。官方 lifecycle daemon 依赖 standalone 安装且仍 experimental，Faryo 改为
  用自己的用户级服务直接监督官方 App Server 进程。

## 目标架构

```text
Browser / installed PWA
        │ authenticated REST writes + cursor SSE reads
        ▼
Gateway (public auth and routing only)
        │ private Owner token
        ▼
Owner ASGI
  ├── session registry and REST validation
  ├── bounded event journal (epoch + sequence)
  ├── browser snapshots and SSE replay/gap
  ├── AppServerClient (one reader, many pending RPCs)
  ├── WebSessionActor per loaded web-managed thread
  └── existing tmux adapter for terminal-managed sessions
        │ private Unix WebSocket
        ▼
official `codex app-server` process
  ├── Codex threads / turns / items
  ├── provider stream
  └── Codex rollout + SQLite projections
```

App Server 是与 Owner 分离的 user service。其启动命令经 `faryo` CLI 动态发现当前有效 Codex
launcher，再 `exec` 官方 `codex app-server --listen unix://…`；systemd unit 不写死 NVM 版本路径。
Socket 目录权限和 Owner token 文件一样采用最小权限。Gateway 不知道 socket 的存在。

## 协议与状态模型

### App Server client

连接生命周期：

```text
stopped → connecting → initializing → ready
   ▲          │              │          │
   └──────── retry/backoff ───┘          ├→ degraded (schema/capability mismatch)
                                        └→ reconnecting
```

实现要求：

- 一个 reader task 是 socket 的唯一读取者；
- request id 映射到 pending future；
- notification 立即路由到对应 `WebSessionActor`；
- server request 路由到审批、用户输入、MCP form 等显式 handler；
- response / error、notification、server request 三类消息不能互相吞掉；
- pending RPC 有 timeout、取消和断线错误；
- 过载 `-32001` 使用有 jitter 的有限退避；
- reconnect 后重新 initialize，按 registry resume 需要的 thread，并生成权威 snapshot；
- 启动时检查当前 Codex 版本及生成 schema 所需 method，不把 0.149.0 的所有字段写死。

### WebSessionActor

每个 loaded web-managed thread 有一个串行 mailbox：

```text
unloaded → loading → idle → running → idle
                  ↘ waiting_for_approval ↗
                  ↘ waiting_for_input ────↗
                  ↘ interrupted / failed
```

Actor 负责：

- thread/session/name/cwd/model/reasoning/service-tier/goal/usage 的内存投影；
- turn、item 和 revision 的稳定 identity；
- delta 聚合、最终 item 替换、生命周期事件；
- 发送幂等账本和排队状态；
- approval / request-user-input 的一次性 action token；
- 重连 snapshot 与 Codex 历史最终收敛；
- 不保存不必要的第二份正文到磁盘。

### 浏览器事件 envelope

```json
{
  "id": "epoch:sequence",
  "epoch": "opaque-runtime-id",
  "sequence": 42,
  "sessionId": "public-session-id",
  "threadId": "opaque-thread-id",
  "turnId": "opaque-turn-id-or-null",
  "itemId": "opaque-item-id-or-null",
  "kind": "item.delta",
  "revision": 7,
  "payload": {}
}
```

正文只存在于需要正文的事件 payload 和当前连接 snapshot 中；日志、指标与控制审计只记录
kind、字节数、耗时、id hash 和结果。

事件 journal 同时限制最大事件数和总字节数。SSE 重连规则：

1. cursor 属于当前 epoch 且在 journal 内：严格按 sequence replay；
2. cursor 太旧：发送 `stream.gap`，随后发送 `session.snapshot`；
3. epoch 不同：发送 `stream.reset`，随后发送 snapshot；
4. replay 写出期间的新 live event 暂存，replay 完成后无缝接续；
5. 浏览器按 event id 去重，revision 旧于现值的更新直接丢弃。

### 流式 item 收敛

- `item/started`：建立稳定 item slot。
- `item/agentMessage/delta`：以 `threadId + turnId + itemId` 追加 accumulator，批量发布 revision。
- `item/completed`：用官方 final text 替换 accumulator，并标为 final；重复完成事件幂等。
- `turn/completed`：刷新 lifecycle、usage、queue 和持久历史游标。
- 断线错过 final：resume/read/list 得到官方 final item，再覆盖同一 stable identity。

## 后端模块拆分

### Owner Web 层决策

Owner 的 Web 层明确迁移到 **Starlette（ASGI Web 框架）+ Uvicorn（ASGI 服务器）**，不再长期
扩展手写的 `ThreadingHTTPServer/http.server`。迁移范围只包括 HTTP 路由、认证中间件、SSE、
lifespan 和静态资产响应；Codex 协议、SessionActor、事件 journal、注册表及业务规则继续保持
与框架无关的普通 Python 模块。这样既使用成熟库处理连接生命周期和背压，也避免把核心状态机
锁进某个框架。

这是渐进替换，不是并行保留两个 Owner：先让新旧 endpoint 共享同一核心模块和契约测试，再把
生产入口切换到 ASGI；完成真实浏览器、断线恢复、认证、附件和部署回归后，删除旧 HTTP 入口。

Owner 现有单文件不能继续承载全部协议逻辑。计划新增：

- `appserver_protocol.py`：版本探测、消息分类、兼容字段抽取、错误类型；
- `appserver_transport.py`：Unix WebSocket、reader/writer、pending RPC、reconnect；
- `appserver_events.py`：有界 journal、cursor、replay/gap、无正文指标；
- `appserver_session.py`：SessionActor、delta/final reducer、snapshot；
- `appserver_requests.py`：approval、user input、MCP form 的 fail-closed 路由；
- `appserver_registry.py`：web-managed session 元数据及重启恢复；
- `appserver_runtime.py`：Codex launcher 解析、socket/service health 与 web-managed 会话注册；
- `owner_asgi.py`：Starlette lifespan、REST/SSE endpoint 装配。

旧 `codex_app_server.py` 的同步调用方逐步迁移到共享异步 client。迁移完成后删除同步 helper，
不保留两套同功能实现。

Owner 从 `ThreadingHTTPServer` 迁到项目已经固定的 Starlette/Uvicorn，使 subprocess/socket/SSE
生命周期可由 AnyIO task group 管理。迁移不改变 URL、认证头、CSP 和 Gateway route。

## 前端增量迁移

不重写整个应用。先把“当前回答尾部”纳入 Preact ownership：

- `StreamingItemStore` 保存 stable item、revision、final 状态；
- EventSource 使用 cursor 和 generation 隔离旧连接；
- delta 在 `requestAnimationFrame` / 自适应短批次内合并；
- streaming Markdown 只提交闭合段落、围栏代码和显示公式，未闭合尾巴安全显示为纯文本；
- final 到达后复用现有统一 Markdown/KaTeX pipeline 完整渲染；
- final 与 streaming 使用同一个 keyed DOM node；
- 活动尾部不参与历史富块脱水，完成后回到现有长历史窗口策略；
- Raw 和 terminal-managed Live from tmux 保持独立，不污染 Chat capture cache。

## 会话模式与迁移

### terminal-managed

- 当前全部已有 tmux/TUI 会话默认保持此模式；
- 发送、interaction、Live from tmux、raw、目录和 TUI geometry 沿用已验证路径；
- 可继续从 Codex rollout 读取结构化最终历史；
- UI 显示 `Terminal` 所有权，不伪装成 App Server streaming。

### web-managed

- 新建时由 App Server `thread/start` 创建；恢复时 `thread/resume`；
- 不创建承载 Codex TUI 的 tmux；
- 使用正式 turn/input/approval APIs；
- UI 显示 `Web` 所有权和 socket/runtime health；
- App Server 不可用时启动动作明确失败，不偷偷回退成另一个写者。

### handoff

第一阶段只保留“新建时选择后端”和只读历史入口，不提供一键双向 handoff。后续只有在官方
提供可验证的即时 unload/attach 契约，或我们能证明原 writer 已退出并释放 thread lock 时，才
增加 handoff。任何自动 attach 都必须 fail closed。

## 安全与隐私

- App Server socket 位于用户私有 runtime/data 目录，父目录和 socket 仅当前用户可访问。
- Owner 是唯一协议客户端；Gateway 只转发既有 allow-listed HTTP 路由。
- 所有写 API 继续要求 Owner token；SSE 不把 token 写入日志。
- server request action token 单次使用、短时有效、绑定 session/request/revision。
- cwd、附件路径和 local image 继续经过既有 workspace/path 安全校验。
- 日志不记录 prompt、回答、diff、命令正文、附件内容或审批理由。
- diagnostics 只公开版本、状态、队列长度、event lag、重连次数和脱敏错误类别。
- 未知 server request 不自动批准；UI 不支持时返回拒绝/不可用，并保留可恢复状态。

## 验收矩阵

| 场景 | 通过条件 |
| --- | --- |
| 正文流 | 首个正文 delta 可见；持续增长；final 原位替换；无整块重复 |
| 数学/Markdown | 流中未闭合 TeX 不破坏页面；完成后与历史 renderer 一致 |
| 工具调用 | delta 不被 tool enrichment 阻塞；tool 状态有稳定 identity |
| Owner 重启 | 活动 turn 继续；Owner 恢复后 snapshot/final 自动出现 |
| 浏览器休眠 | cursor 内 replay；cursor 外 gap+snapshot；无硬刷新 |
| 慢客户端 | 有界队列；只断慢连接；Owner/App Server 不被拖死 |
| 双写者 | Web-owned thread 的 TUI resume 明确失败；不会同时接受输入 |
| 幂等发送 | 同 submission 重试只产生一个用户 item/turn |
| 审批/输入 | 一次性 action；重复点击无副作用；未知 request 不自动放行 |
| 长历史 | 快速滚动、resize 和跨屏无长时间主线程阻塞 |
| 移动端 | 键盘出现时历史与 composer 同一可视 viewport，无像素猜测回归 |
| 认证 | 未认证 REST/SSE 均拒绝；socket 不对网络监听；敏感值不进日志 |
| tmux | 既有 terminal-managed 行为与 geometry 完全不变 |

## 量化门槛

- delta 到浏览器发布批次默认不高于一帧一次，并能在后台/高负载时自动降频。
- journal 默认同时受事件条数和字节数约束；压力测试后记录最终阈值。
- pending RPC、server request 和 replay buffer 全部有 timeout/上限。
- 普通局域网首个正文 delta 目标 p95 小于 500 ms；代理网络单独记录，不把公网 RTT
  误判为 Owner 延迟。
- 10,000 个匿名历史块的逻辑加载不等于 10,000 个富 DOM 节点；现有有界渲染门继续通过。
- browser reconnect 不产生重复 item；最终 transcript hash 与冷加载结果相同。

## 回滚策略

- feature 分支在全部门通过前不合并 `main`。
- 新后端由会话记录明确选择；出现问题可把新建默认值切回 terminal-managed，不迁移已有
  web-managed writer。
- App Server unit 与 registry 新增文件独立，卸载保留 Codex 历史并停止 socket 服务。
- Owner API 和前端资产保留版本兼容窗口；回滚版本不会删除 Codex rollout。
- 不用 `git reset --hard` 或删除用户会话；发布回滚走既有 checksum/previous release 路径。
