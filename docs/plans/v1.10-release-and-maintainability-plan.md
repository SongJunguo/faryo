# Faryo v1.10 Release and Maintainability Plan

状态：进行中

开发分支：`feature/v1.10-maintainability`

基线：Faryo `1.9.1`，`main` 提交
`17cf3b9cbef309f9ad9ddbf7702cd23833e82280`

开始日期：2026-08-22

## 1. 背景与结论

Faryo 1.9 已经完成 Codex App Server 正文流、Owner ASGI、单写者会话、断线恢复、
Preact 交互壳和 tmux 兼容路径。当前运行健康，下一阶段不需要再做一次框架重写。

现在最值得处理的三个问题是：

1. `main` 已是 1.9.1，但最新公开 tag/Release 仍停在 1.6.7；新用户按 README
   下载会得到旧架构，发布入口与源码事实不一致。
2. 维护成本仍集中在少数热点：Owner `server.py` 约 3,700 行、Owner `app.js`
   约 2,600 行，Gateway `workbench.js` 约 1,800 行。已有服务模块和 Preact 岛，
   但 composition root 仍承担过多转换、状态拼装和 DOM 协调。
3. 项目精确固定 Python、Node 和 GitHub Actions 依赖，但缺少自动依赖更新入口、
   静态安全扫描和显式 Ubuntu 22.04 兼容门。Faryo 是远程控制面，这些属于值得
   自动化的维护工作。

本阶段采用渐进拆分和可验证的供应链加固，不增加原生 App、Web Push、多人协作、
第二套后端或不安全的 TUI/Web 自动接管。

## 2. 用户可感知结果

- GitHub 的 Latest Release 与 `main`/README 不再相差多个版本；安装器默认获得当前
  App Server 流式架构。
- 更新依赖或 Codex 后，CI 能更早发现 Python、Node、浏览器 bundle、协议和 Ubuntu
  22.04 兼容回归。
- 后续修复发送、历史、流式输出或交互菜单时，修改范围更小，不必继续扩大两个前端
  composition root 或 Owner 主服务文件。
- 部署、普通刷新、移动键盘、Markdown/TeX、长历史、认证和 tmux 几何保持现状。

## 3. 非目标

- 不把 Python 后端改写成 Go、Rust 或 Node。
- 不把整个前端一次性改写成 React/Preact，也不虚拟化已经通过验收的 rich transcript。
- 不删除 terminal-managed/tmux 兼容模式。
- 不实现未经官方协议证明安全的 Web/TUI 双向 handoff。
- 不实现可编辑 pending queue、后台 Web Push、语音、公共分享或原生移动 App。
- 不更改 Cloudflare Access、Gateway Cookie 或 Owner token 的操作者配置。
- 不记录 prompt、answer、会话正文、私有路径、账号、域名、Token 或 Cookie。

## 4. 不可回归约束

1. **单写者**：Web-managed thread 只能由持久 App Server actor 写入；terminal-managed
   thread 只能由现有 TUI 路径写入。
2. **正文真相**：Codex rollout/App Server history 仍是持久正文来源；Faryo 不建立正文数据库。
3. **认证**：Browser → identity edge → Gateway → Owner → Unix socket 的边界不变；Owner、
   Gateway 继续只监听 loopback，App Server 不增加 TCP 监听。
4. **可靠发送**：submission ID、快速 ACK、重试幂等、失败草稿和 queued Send now 不回归。
5. **渲染**：Markdown AST、KaTeX、Shiki、Raw/Chat 隔离、复制原始 Markdown/TeX 不回归。
6. **长历史与移动端**：有界 rich DOM、前插锚点、问题导航、原生 viewport-resize 和透明
   composer 不回归。
7. **普通刷新**：可变资产继续自动版本化；新 tab 或普通 reload 即可获得新代码。
8. **tmux**：升级、服务重启和测试不得修改既有 pane PID、名称、宽高或 TUI wrapping。
9. **公开隐私**：计划、fixture、CI 日志和 Release 不出现真实会话、私有路径或凭据。

## 5. 工作流 A：补齐 1.9.1 稳定发布

1. 以当前已验证的 `main` 提交创建不可变 `v1.9.1` tag，不让后续 v1.10 改动混入。
2. 复核版本四处一致、Release notes、source archive、checksum 和 bootstrap installer。
3. 运行 canonical source gate、公开差异隐私扫描和 GitHub Release workflow。
4. 在全新临时目录通过 Release 资产安装/doctor/update/rollback 合同；不触碰现有私有数据。
5. 验证 GitHub `releases/latest` 指向 1.9.1，README 安装示例不再指向 1.6.7。

## 6. 工作流 B：Owner 后端热点拆分

先用函数调用图和现有测试确定边界，再移动代码。目标不是追求小文件，而是让路由、
状态投影和领域服务只有一个所有者。

优先候选边界：

- session/history catalog：Codex thread 列表、标题、cwd、archive/search/page 投影；
- status/workbench projection：tmux、App Server、goal、usage、Git 和 ownership 的只读合并；
- launch/resume policy：目录 token、context window、运行时 ownership 和幂等 launch receipt；
- composition wiring：`server.py` 只装配配置、服务对象和兼容导出，不重新实现领域规则。

实施规则：

- 新模块先通过现有函数的契约测试，再切调用点；
- 不保留两份同功能实现或永久 forwarding wrapper；
- 不把 ASGI Request/Response 对象传入领域模块；
- 可测试纯逻辑使用标准库 dataclass/TypedDict，不为搬文件引入新运行时框架；
- terminal-managed helper 必须在命名和类型上保持只读/兼容边界，不能成为第二个 writer。

量化目标：`server.py` 至少净减少 20%，且迁出的每个模块有聚焦单元测试；如果调用图
证明某一候选边界会增加循环依赖，则记录证据并选择更窄边界，不用行数目标强迫错误拆分。

## 7. 工作流 C：Owner/Gateway 前端 composition root 收敛

保留当前 Preact 岛和高性能 imperative transcript，不做全量 framework migration。

1. 盘点 `app.js` 与 `workbench.js` 的网络、状态、渲染和事件责任。
2. 优先把 App Server stream/snapshot/revision 投影、session ownership 和可复用 API 数据
   normalization 移入严格 TypeScript 或可独立 Node 测试的 ES module。
3. `app.js` 只保留 rich Markdown/TeX、Raw、Live tmux、历史岛之间的 composition adapter；
   不让 Preact 再实现第二套正文 renderer。
4. Gateway 继续让 Preact keyed lists 拥有动态卡片；`workbench.js` 不重复拼接这些节点。
5. 每个新模块需有 stale generation、out-of-order event、ordinary reload 和 inert-text 测试。

量化门：至少移除一个完整的状态责任，而不是把同样闭包机械切成多个文件；生成 bundle
必须可复现，gzip 预算、许可证文件和 CSP 不变或有明确记录。

## 8. 工作流 D：依赖与供应链自动化

1. 增加 Dependabot（或经审计后更合适的等价工具）处理 npm、pip 与 GitHub Actions，
   使用低噪声的每周分组 PR，不自动合并。
2. 对第三方 GitHub Actions 固定完整 commit SHA，并保留可读版本注释；更新由 bot 提 PR。
3. 增加官方 CodeQL Python/JavaScript-TypeScript 扫描；无权限或平台限制必须显式报告，
   不能假装通过。
4. CI 增加 Ubuntu 22.04/Python 3.10 的真实最低支持 lane，并保留当前 Python 3.13 lane；
   避免把完整浏览器矩阵重复到每个组合导致 CI 失控。
5. 继续执行 `npm audit`、锁文件一致性、bundle byte-compare 和依赖许可证账本检查。
6. 自动化只处理公开依赖元数据，不读取部署配置、会话或私有文件。

## 9. 工作流 E：版本化浏览器 API 契约

1. 列出 Owner → browser 的 status、snapshot、event、interaction、history 和 error envelope。
2. 为跨 Python/TypeScript 的核心 envelope 建立一个版本字段和匿名 fixture；优先使用
   TypedDict/TypeScript 类型与现有契约测试，不默认引入 Pydantic。
3. 未知向后兼容字段可忽略；未知写 action、server request 或 ownership 值 fail closed。
4. Codex 升级后的 capability probe 必须区分 optional drift 与 required-method breakage。
5. 浏览器旧连接通过 generation/epoch/revision 被隔离，不能把旧响应写入新 session。

## 12. 回滚与停止条件

- 所有实现留在 feature 分支，完成门禁前不合并 `main`。
- 1.9.1 tag 指向改造前已验证提交，可作为稳定回滚点。
- 后端/前端每次迁移先共享契约测试，再删除旧实现；不使用 destructive Git 操作。
- 如果拆分导致循环依赖、bundle 重复 renderer 或性能门失败，回退该子阶段并保留更窄接口，
  不用“已经投入很多”作为继续的理由。
- 如果 CodeQL/Dependabot 因仓库权限不可启用，保留配置和本地验证证据，明确记录需要的
  GitHub 操作者动作。
- 更新和部署失败必须自动回到上一健康版本，且不得停止或重建既有 Codex/tmux 会话。

## 13. 公开与隐私规则

- 计划、提交、PR、Release notes 和 fixture 只使用匿名 session、临时目录与假凭据。
- 不提交真实 hostname、邮箱、Cloudflare 组织信息、Token、Cookie、密码、会话正文、私有
  workspace 路径或真实 tmux 名称。
- 诊断只保留版本、功能标志、计数、耗时和脱敏错误类别。
- 发布前对新增及修改文件执行 credential/private-path/body 关键词扫描，并人工复核命中。

## 14. Phase 0 基线证据

- `main`/`origin/main` 为 1.9.1 的干净提交，最近一次 Source CI 在 Python 3.10 与
  Python 3.13 均通过；公开仓库的 Latest Release 仍是 1.6.7。
- canonical source gate 通过：220 个 Owner、118 个 Gateway、60 个 CLI Python 测试，
  以及 Ruff、ESLint、Prettier、TypeScript、Node/browser tests 和可复现 bundle。
- 部署的 1.9.1 `faryo doctor` 为 24 OK、0 warning、0 failed；App Server、Owner、Gateway
  三个服务 active，只有 Owner/Gateway 在 loopback TCP 监听。
- 八个既有 tmux pane 的名称、PID 和 geometry 已生成仅供本轮前后比较的本地摘要；不把
  名称或其他私有会话信息写入仓库。
- 当前 tracked footprint 为 451 个文件、约 7.42 MB；主要热点为 Owner `server.py`
  3,747 行、Owner `app.js` 2,602 行和 Gateway `workbench.js` 1,835 行。
- 当前生成 bundle 预算实测约为 Owner 10.8 KiB gzip、Gateway 7.4 KiB gzip；后续仍以
  构建器固定的正式阈值为验收依据。
