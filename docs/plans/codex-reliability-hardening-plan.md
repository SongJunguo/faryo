# Faryo Codex Reliability Hardening Plan

更新时间：2026-08-18

状态：维护加固完成（2026-08-18）

开发分支：`feature/deepseek-inspired-ui`

计划索引：[`README.md`](README.md)

## 1. 目标

在不改变 Codex TUI、tmux 窗口尺寸和现有权限策略的前提下，把 Faryo 的 Codex 路径
从“当前可用”加固为可承受超长会话、服务重启、手机长时间离线和异常 Markdown 的
长期运行实现，并清理仍然暴露内部协议细节的界面。

本计划以以下结果为完成条件：

1. 数百 MB 的 rollout JSONL 不再被一次性读入内存，也不在状态刷新时全量扫描。
2. 网页只保留显示所需的最近完整 turn；缓存有明确的行数、字符数和会话数上限。
3. 已确认发送的消息在 Owner 重启或手机离线后仍能按消息 ID 去重。
4. `<oai-mem-citation>` 等内部元数据以简洁、可折叠的说明展示，不泄露 rollout UUID，
   也不混入复制的回答正文。
5. 单条 Markdown/KaTeX 渲染失败只让该条消息降级为安全纯文本，不中断后续实时更新。
6. 本机直连 Owner 加载后从地址栏移除 Token；SSE 不再依赖查询参数认证。
7. 历史分页、文件投递保留和路由显示不再随着数据增长持续退化。

## 2. 明确排除

- 不开发或调优 Claude Code 路径；本轮只保证既有 Claude 代码不被破坏。
- 不修改 Codex/Claude 权限参数、Gateway Access 24 小时会话或独立 MFA 选择。
- 不修改任何 Codex tmux 窗口宽高，不调用 `resize-window`。
- 不替换已经确认可用的复制按钮。
- 不把完整 DeepSeek Harness/Cordis/React 运行时搬入 Faryo。

## 4. 实施阶段

### A. 有界 rollout 状态（P0）

实现：

- 首次打开大文件时从最后一个完整 JSONL 记录向前扫描，只取满足显示预算的最近 turn。
- 以文件设备号、inode 和完整记录偏移为增量游标；保留写入中的半行。
- 当未读间隔异常大时重新建立尾部基线，不读取整个差值。
- 每个路径缓存最多保留固定行数、字符数；全局最多保留固定数量的活动路径。
- 在同一次增量解析中保存最新 `token_count`，删除状态接口的全文件扫描。
- 文件替换、截断和消失时保持安全重建或短期使用已有尾部。

验收：

- 以至少 250 MB 的稀疏或合成 JSONL 做冷启动压力测试，峰值内存显著低于文件大小。
- 最新完整 user/assistant turn、Markdown 和 TeX 不丢失；半行完成后才出现。
- 状态请求不再随总历史文件大小线性增长。
- 多会话并发读取互不串行阻塞，缓存淘汰后可正确重建。

### B. 持久化发送幂等（P0）

实现：

- 在 Owner 私有数据目录保存最小发送回执：消息 ID、会话、内容 SHA-256、确认状态和时间。
- 不保存消息正文；文件权限为 `0600`，目录权限为 `0700`，原子替换写入。
- 去重窗口扩大到 48 小时，并在启动/发送时惰性清理过期回执。
- Owner 重启后，同一消息 ID 与摘要返回 `duplicate=true`；ID 被不同内容复用时拒绝。
- 已确认 paste、尚未确认 submit 的中间态也持久化；只保存队列基线和 rollout
  文件身份/偏移，不保存正文或私有文件路径。
- 未确认的 paste 状态不伪装为成功；重启或重试后只有出现新的 rollout/队列证据才转为成功，
  否则继续返回歧义状态并保留浏览器和 TUI 草稿。

验收：

- 隔离 Owner 完成“首次已投递、清空内存模拟重启、再次请求不写 tmux”的测试。
- 过期回执被清理，损坏回执不导致 Owner 启动或发送失败。
- 既有 20 条真实浏览器发送矩阵、504 歧义恢复和失败草稿测试继续通过。

### C. 内部引用展示与渲染错误边界（P1）

实现：

- 识别完整 `<oai-mem-citation>` 块，将正文与内部引用分离。
- 正文正常进入 Markdown/KaTeX；引用显示为折叠的 `Memory references` 卡片。
- 只显示条目数量和经过转义的简短说明；不显示 rollout UUID，不执行其中的 HTML。
- 复制回答时复制正文，不附带内部 XML。
- 每个消息块独立捕获 Markdown、KaTeX 和稳定块错误，失败时显示安全纯文本及轻量提示。
- 整个 capture 渲染再增加总兜底，确保后续 SSE 更新仍可继续。

验收：

- 真实形状、空条目、损坏或未闭合引用块均不出现原始 XML/XSS。
- 引用前后的公式、表格和代码继续正常渲染。
- 人为令 renderer 抛错后只降级对应消息，下一条正常消息能够恢复富文本。
- 复制按钮的现有样式和交互保持不变。

### D. Owner 认证与安全响应头（P1）

实现：

- 以带 `X-Owner-Token` 的流式 `fetch` 替代无法设置请求头的原生 `EventSource`。
- 直连页面从查询参数取得 Token 后存入当前标签页的 `sessionStorage`，立即用
  `history.replaceState` 清理地址栏；Gateway 路径仍由服务端注入 Token。
- SSE parser 支持分片、多个 data 行、75 秒服务端轮换、AbortController、代际丢弃、
  指数退避和 HTTP fallback。
- Owner HTML/API/文件响应统一增加 `Referrer-Policy`、`X-Content-Type-Options`、
  framing 限制、受限 Permissions Policy 和适配本地资源的 CSP。

验收：

- 直连页面首次加载后 URL、DOM 和后续 `/api/events` 请求均不含 Token。
- 页面刷新仍能从当前标签页恢复认证；新标签页必须重新由合法入口取得 Token。
- Gateway 代理、受保护文件/图片、SSE 恢复及 401 边界继续通过。

### E. 数据生命周期与真实分页（P2）

实现：

- Codex 非活动历史直接在 SQLite 查询中分页，不先构造全部历史再切片。
- 活动会话保持完整显示，并与历史总数、偏移独立。
- Gateway bridge package 增加私有可配置保留期和惰性清理；默认清理已投递旧包，
  pending 包使用更长保护窗口。
- Projects 的 Owner 选择器由运行时 route label 生成，不硬编码 `TXY/HP/PC`。

验收：

- 40 页以上历史的第 1、3、末页内容、总数和活动区一致。
- 分页请求成本主要取决于单页和活动会话，而不是完整历史数量。
- 清理只触及 bridge package 根目录内已解析的包，不跟随符号链接、不删除待发送新包。
- 当前私有部署继续显示操作者配置的工作站名称；公开仓库不写入真实机器信息。

### F. 发布回归（P0）

- 使用 `conda env list` 确认并通过 `faryo` 环境运行全部 Python 测试。
- 运行 Markdown AST、稳定块、发送协议和发布包检查。
- 运行 250 MB 级长历史压力测试并记录时间、RSS 和缓存上限。
- 运行 390x844、1440x900 Chrome；条件具备时补 Edge。
- 验证 Markdown、KaTeX、记忆引用卡片、错误降级、SSE、刷新、后台恢复、附件和分页。
- 隔离测试会话执行发送/504/重启去重矩阵，不向用户真实会话注入测试内容。
- 部署 Owner/Gateway，核对健康、日志、所有活动 Codex 结构化来源和 tmux 尺寸不变。
- 执行公开差异隐私扫描、`git diff --check`，只推送个人 `origin`。

## 6. 完成结果

- Owner 与 Gateway 已从当前功能分支重新部署；公网入口仍由既有 Cloudflare Access 保护。
- 五个活动 Codex 会话在部署后均继续使用结构化 JSONL，未修改任一 tmux 窗口尺寸。
- Markdown、GFM 表格、KaTeX 块/行内公式和按需代码高亮继续使用统一的本地 AST 管线。
- 实时连接上限从 6 调整为 16，并加入 10 秒注释心跳；隐藏标签页仍主动释放连接，失败时保留 HTTP 轮询后备。
- 当前部署没有 bridge package，因此启用保留期清理时未删除任何既有文件。

### 2026-08-16：Codex 0.147 输入状态机修复

- 真实复现证明原 504 多为确认假阴性：消息已经离开输入框，Codex 正在启动 MCP
  或执行当前轮，但 Owner 仍在等待 rollout 落盘，并把工作态光标误判为未提交。
- Codex 0.147 的活动输入框在空闲时使用 `›`，工作时使用 `»`；Owner 现在同时识别，
  并使用 ANSI dim 样式区分真实草稿与旋转占位文本，不再依赖自动换行后不可靠的
  `cursor_x`。
- 空闲 Codex 使用 `Enter` 提交；工作中的网页消息使用 `Tab` 加入下一轮队列。每次
  重试前重新读取当前 TUI 状态，只有原文本仍留在活动输入框时才再次发键。
- 接受证据按强度覆盖 rollout 中新增的精确 user event、queued-follow-up 中新增的精确
  文本；仅空闲态 `Enter` 允许以原文本离开活动输入框作为提交证据。工作态 `Tab` 不再把
  输入框清空或旧的同文队列项误认成新投递。
- 单元测试、发布检查、20 条浏览器发送/网络恢复/歧义响应矩阵、真实空闲提交、真实
  工作态排队和 63 列多行草稿防覆盖均通过；既有 Codex tmux 尺寸保持不变。

### 2026-08-16：发送并发、重启与跨会话纠偏

- 长时间确认锁从 Owner 全局锁拆为按 tmux 会话串行；不同会话可以独立投递，同一会话
  仍保持单一 composer 的顺序约束。同一 client message ID 另有精确、带引用计数的临时
  锁，跨会话复用不会绕过去重/冲突检查，无关 ID 也不会因哈希碰撞互相阻塞。
- 队列确认改为比较提交前后的精确文本出现次数，并在活动 composer 前停止解析；页面中
  已存在的同文队列项或当前输入框副本不再制造假成功。
- v2 私有发送记录持久化 pasted 中间态。Owner 重启后，如果输入框已经消失但没有新的
  rollout 或队列证据，Owner 返回 HTTP 504 且不再次 paste/发键，不再生成无证据的
  `recovered` 回执。
- 浏览器把原始 session、消息 ID、正文和附件路径固化为一次提交快照。180 ms 恢复重试、
  12 秒请求超时和延迟响应都继续指向原始 session；晚到的 A 会话响应不会清空 B 会话
  即使文本完全相同的独立草稿。
- 新增 390x844 匿名双会话 Chrome 回归：重试期间切换和响应挂起期间切换均只向 A 投递，
  A 收到 2 次、B 收到 0 次，两个临时 tmux 窗口尺寸保持不变。

### 2026-08-18：公式密集长回答不再吞掉近期历史

- 根因不是 rollout、SQLite 映射或结构化来源丢失，而是完整 turn 选择器把 `lines=320`
  当成硬限制。一轮公式密集回答可有近千个 Markdown 源行但只有约 9 KB；加入它会使
  行预算溢出，选择器便只保留最后一轮，让页面看起来像历史被清空。
- 行预算现在是软限制：在它之外仍以有界 rollout 尾部中最近 12 个完整 turn 为保留目标。
  单独的 512 KiB 字符硬上限约束浏览器载荷；最新完整 turn 即使单独超过上限也不会被
  截成半条回答。
- rollout 尾部缓存使用同一最小 turn 规则和既有 4 MiB 字符上限，继续保持增量读取、
  完整 JSONL 记录边界和大文件有界扫描。
- 新增公式密集 turn、硬字符上限和缓存越过软行预算三类回归；测试夹具只含匿名内容。
- 263.3 MiB 最大 rollout 冷读取约 0.0025 秒、进程峰值约 41.5 MiB，说明扩大近期 turn
  保留没有退化为全文件读取。
- 部署后的隐私安全检查中，同一活动会话从 1 个 user turn 恢复为 11 个，结构化来源保持
  `codex-jsonl` 且无警告；390×844 Chrome 的 Markdown/KaTeX 检查通过，所有 Codex tmux
  窗口尺寸保持不变。

## 7. 回滚与公开仓库边界

- 所有实现只进入当前个人 fork 功能分支；`upstream` 只用于追踪原作者，不推送。
- 每个阶段以测试和计划记录形成可审查提交；必要时按阶段回滚，不删除用户数据。
- 测试夹具只使用匿名公式、随机消息 ID、临时目录和一次性 tmux 会话。
- 私有运行时回执、附件、Access 配置、邮箱、域名、Token、Cookie 和真实对话不进入 Git。
