# Live Stream Resilience Plan

状态：已完成、部署并通过 v1.6.6 发布门禁

## 问题

Owner 的本地 SSE 会持续发送捕获变化并每 10 秒发送心跳，但浏览器客户端过去只在
`fetch` 明确失败或响应结束时重连。移动浏览器休眠、网络切换或中间代理可能留下一个
仍为 open、却不再交付字节的半开连接。客户端同时停用了轮询后，结构化对话和
`Live from tmux` 会一起停在旧画面，直到用户重新加载页面。

## 范围

1. 为浏览器 SSE reader 增加有界的心跳空闲超时，超时后走既有退避重连。
2. SSE 正常时保留低频安全捕获；未变化的结果不得触发 Markdown/TeX 重渲染，且较旧的
   安全响应不得覆盖更新的事件帧。
3. 在 `pageshow`、窗口重新获得焦点、网络恢复和页面重新可见时，立即抓取当前状态并
   重建实时流。
4. 保持已有认证头、Gateway 路由、历史分页、可靠发送、tmux 会话和终端几何不变。

## 非目标

- 不把 SSE 替换成 WebSocket。
- 不修改 Codex TUI 的宽高或会话进程。
- 不以无限高频轮询掩盖连接状态。
- 不把真实域名、账号、Token、会话名或对话正文写入公开证据。

## 验收标准

- 正常心跳不会导致误重连。
- 半开无心跳流能自动进入 fallback 并重新建立 SSE。
- SSE 活跃时安全捕获持续存在，但相同内容只渲染一次。
- 后台/前台、BFCache、焦点和联网恢复路径不需要强制刷新。
- 完整 source gate、真实 Owner/Gateway 浏览器回归和部署后 tmux 几何检查通过。

## 当前证据

- 定向 Node 测试覆盖半开流、持续心跳、去重安全捕获和旧响应隔离，7 项通过。
- 真实 Chrome 回归会在内存中制造无心跳半开流，并检查安全捕获、自动重连、联网恢复、
  BFCache `pageshow` 和普通重新加载；不读取或输出对话正文。
- 真实 Owner 与经过 Gateway SSE 代理的 390x844 浏览器路径均通过故障注入：每次观察到
  7 次有界捕获、4 次流连接，并在普通重新加载后取得当前版本资产。
- 完整 source gate 通过 Owner 195、Gateway 115、CLI 56，以及格式、lint、TypeScript 和
  本地浏览器资产检查。
- GitHub Source CI `32469357084` 在 Python 3.10 与 3.13 上通过同一套门禁。
- 本机 v1.6.6 部署通过 22 项 doctor 检查，部署前后的既有 tmux pane PID 与几何保持不变。
